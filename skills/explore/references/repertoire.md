# Repertoire: what exists, and where to find it

The names below are retrieval cues. They bring possibilities into consideration, so you can choose, combine, adapt or invent for the brief. They are neither a complete account of design nor a list of things a page should contain. This file grows as new sources turn up; add to it when one earns its place.

## Component and effect families

The full top-level category list of the [21st.dev catalogue](https://21st.dev/community/components), checked 2026-09-21. The grouping follows that source for lookup only.

**UI components:** accordions, AI chats, alerts, avatars, badges, buttons, calendars, cards, carousels, charts and data viz, checkboxes, cursors, dashboards, date pickers, dialogs and modals, dropdowns, empty states, file trees, file uploads, forms, globes, grids and bento, icons, inputs, links, lists, menus, notifications, numbers, onboarding, paginations, popovers, profiles, progress, radio groups, search bars, selects, sidebars, sign-ins, sign-ups, sliders, spinner loaders, tables, tabs, tags, text areas, toasts, toggles, tooltips.

Expressive families with their own collections:

- [ASCII art](https://21st.dev/community/ascii): character-built portraits, scenes and patterns.
- [Gradients](https://21st.dev/community/gradients): atmospheric fields, layered colour, ribbons and bands, dithered patterns, focal glows, rings and sweeps.
- [Shaders](https://21st.dev/community/shaders): flow fields, waves, smoke, silk, aurora, caustics, mesh drift, metaballs, plasma, warped stripes, halftone, paper texture, water, image dithering, noise, liquid metal, glass, light rays, Voronoi.

A treatment's value depends on how it changes perception, attention, atmosphere or interaction in this project. Weigh expressive treatments alongside composition, type and content from the start, rather than decorating a finished generic layout.

## Using a reference

Search from the project's intended experience, not from a style name, and go beyond these three sites when that helps. Open the original work or the primary documentation before adopting an approach, since catalogue descriptions are leads. A recording can show an effect without establishing how it was built or how it performs, so keep observed behaviour separate from inferred implementation.

Borrow the mechanism that serves the project and adapt it to the project's identity, content and stack. Liking an example does not make its whole visual identity the target. When reusing third-party code, check its dependencies and licence. A catalogue listing says nothing about accessibility or performance in this project; the normal verify pass covers that.

Record the chosen sources, why the mechanism fits and its trade-offs in `DESIGN-BRIEF.md`, so later work understands the decision without repeating the search.
